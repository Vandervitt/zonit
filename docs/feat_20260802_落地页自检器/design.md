## 一、为什么做这个

前四个 PR（#155–#158）建立的是**内容资产**，回报周期 3–6 个月。自检器是清单上唯一能**立刻**产出精准线索的一项：

- 能贴出落地页 URL 的人，一定正在投放——这是最强的意向信号，比任何表单筛选都准
- 报告本身可截图转发，在投手群里天然传播
- 它把刚发布的 5 篇合规文从「读完就走」变成「读完去测一下」，是内容簇的变现落点
- 面向的是客群 A（投手 / 代运营），而前四个 PR 全部服务于客群 B（本地服务商走搜索）

## 二、非目标（红线，不可协商）

**报告不得给出评分，不得声称「会过审」或「不会过审」。**

这既是责任问题也是可信度问题：结果承诺正是我们自己刚写的 5 篇文章教读者不要相信的东西。工具一旦输出「✅ 通过」，等于自打嘴巴，且在页面实际被拒时我们要为那个承诺负责。

对应的产品约束：

- 输出形态是「**审核常盯的地方** + **你这页的实际情况**」，不是分数、不是红绿灯总评
- 每条发现都必须能追溯到一条**可核实的客观事实**（链接返回 404、像素在同意前触发），而不是主观判断
- 需要人判断的项（功效宣称是否合规、文案是否过度承诺）**不做自动判定**，只标「这几句值得重读」并链到对应文章

其他非目标：

- 不做 SEO 体检（关键词、外链、排名）——那是大路货，且稀释定位
- 不做整站爬取，只测单个 URL
- v1 不做「一组页面雷同度对比」（见第九节分期）

## 三、用户旅程

```
读到合规文 / 群里看到报告截图
  → 落到 /tools/landing-page-check
  → 贴 URL，无需登录
  → ~5s 出 A 档结果；含像素的页面 B 档随后补上
  → 报告可分享（不可猜测 token 的公开链接）
  → 想比较多张页面的结构雷同度 → 需要账号（v2，楔子埋点）
```

## 四、检查项（v1 冻结）

### A 档 · 确定性事实（纯抓取，成本极低）

每条都是是非题，不需要判断，也因此不会误报。

| 检查 | 判据 | 为什么审核在意 |
|---|---|---|
| 隐私政策链接 | 存在且返回 2xx | 最廉价的拒审原因，404 极常见 |
| 服务条款链接 | 存在且返回 2xx | 平台目标网址要求 |
| 跳转链 | 逐跳记录，末端可达 | 中间环节挂掉是隐形杀手 |
| robots.txt | 是否屏蔽主流广告/搜索爬虫 | 屏蔽 = Google 无法评估 = 直接拒登 |
| 经营主体与联系方式 | 页面是否含邮箱 / 电话 / 地址 | 着陆页体验的常见缺项 |
| HTTPS | 是否 https、证书是否有效 | 非 https 本身即为发现项 |
| 页面体积与阻塞资源 | HTML 体积、同步脚本数 | 速度粗判；**不做完整 LCP** |
| 版权年份 | 是否明显过期 | 「无人维护」的弱信号，低优先级展示 |

### B 档 · 需要浏览器（v1 只做一项）

| 检查 | 判据 |
|---|---|
| **像素是否在取得同意前触发** | 记录网络请求时序与同意组件交互前的出站请求 |

只做这一项的理由：它是报告里唯一会让人「哦操」并截图转发的发现，而其余浏览器类检查（LCP、插页、首屏）价值递减但成本相同。

### C 档 · 不做自动判定

功效宣称、收益承诺、过度承诺类文案。做法：用关键词命中**标出句子**，措辞一律为「这几句值得对照政策重读」，并链到对应文章。**不给结论**。

## 五、架构

```
/tools/landing-page-check          公开页（+ /zh 镜像）
        │  POST
        ▼
POST /api/tools/page-check         限频 → SSRF 校验 → 抓取 → A 档检查
        │                                        │
        │                          静态预筛：检测到像素？
        │                                        │ 是
        │                                        ▼
        │                            Vercel Sandbox 起 Chromium
        │                            记录同意前的出站请求 → B 档结果
        ▼
落库 page_check_reports（token 可分享）
        ▼
/tools/landing-page-check/r/<token>   公开报告页（+ /zh 镜像）
```

**关键设计：静态预筛控成本。** 只有静态检测到像素代码时才起浏览器——没有像素的页面根本没有「同意前触发」可测。按经验这能把浏览器调用量砍掉相当一部分，是成本控制的主要杠杆。

## 六、安全：SSRF 防护（v1 必须完整，不可后补）

接受任意用户 URL 在服务端抓取，是教科书级 SSRF 入口。以下每一条都是必需项。

### 6.1 入口校验

- **仅 `https:`**——`http:`、`file:`、`gopher:`、`data:` 一律拒绝（非 https 本身作为发现项呈现，而不是去抓）
- 拒绝带凭据的 URL（`user:pass@host`）
- 仅允许 443 端口
- 拒绝 IP 字面量形式的主机名（强制走域名，减少直连内网的路径）

### 6.2 DNS 解析后的地址校验

解析主机名，取回**全部** A/AAAA 记录，任一落入下列范围即拒绝：

| 协议 | 拒绝范围 |
|---|---|
| IPv4 | `0.0.0.0/8` `10/8` `127/8` `169.254/16`（含云元数据 169.254.169.254）`172.16/12` `192.168/16` `100.64/10` `224/4` `240/4` |
| IPv6 | `::1` `fc00::/7` `fe80::/10` `::/128` |
| 双栈 | IPv4-mapped IPv6（`::ffff:a.b.c.d`）必须**先解包再按 IPv4 规则判**——这是最常见的绕过 |

### 6.3 防 DNS rebinding（TOCTOU）

校验通过的是「解析出的 IP」，实际连接必须**连到那个已校验的 IP**，而不是重新解析域名。实现方式：给 undici Agent 传自定义 `connect.lookup`，返回已校验的地址；不允许连接阶段二次解析。

### 6.4 重定向

- **不使用自动跟随**（`redirect: "manual"`）
- 手动逐跳跟随，**每一跳都重新执行 6.1–6.3 全部校验**
- 最多 5 跳；超出即中止并作为发现项报告
- 跳转到非 https scheme 一律中止

### 6.5 资源上限

- 连接超时 5s，总超时 10s
- 响应体上限 2 MB，流式读取，超限即 abort（不得先读完再判断）
- 仅接受 `text/html` 与 `text/plain` 内容类型

### 6.6 浏览器侧

Sandbox 内的 Chromium 同样只能访问已校验的最终 URL，且 Sandbox 本身是隔离环境——这是选择 Sandbox 而非在函数内直接跑浏览器的一个附带好处。

## 七、滥用与成本控制

- **限频复用 `lib/rate-limit-db.ts`**（已落库、跨实例，`/api/leads` 在用）。建议：同 IP 每小时 5 次、每日 20 次，两个桶叠加
- 同一 URL 的报告在 15 分钟内直接返回缓存结果，不重复抓取
- 浏览器检查仅在静态预筛命中像素时触发
- 报告 30 天后自动清理，挂进现有的 `app/api/cron/daily`（已有 `pruneRateLimitHits` 等同类子任务，模式现成）

## 八、数据模型

新增迁移 `040_page_check_reports`：

| 字段 | 说明 |
|---|---|
| `id` | text 主键，**nanoid 且不可猜测**（⚠️ 注意默认字母表含 `_`/`-`，URL 场景需确认无歧义，见平台子域那次的教训） |
| `url` | 被检查的 URL |
| `host` | 归一化主机名，用于缓存与滥用分析 |
| `locale` | 生成报告时的语言 |
| `findings` | jsonb，检查项结果数组 |
| `browser_ran` | boolean，是否实际起了浏览器（用于成本核算） |
| `ip_hash` | 哈希后的来源 IP，仅用于滥用溯源，不存明文 |
| `created_at` / `expires_at` | 保留 30 天 |

⚠️ 全库 id 均为 text，不要做整型假设。

## 九、分期

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **v1** | A 档全部 + B 档一项（像素/同意时序）+ 公开报告页 + 双语 | 本文档通过 |
| **v2** | 一组页面的结构雷同度对比（DOM 结构哈希 + 素材重用率）——**需要账号，楔子埋点在此** | v1 有真实使用量后再定指纹算法 |
| **v3** | 与已发布页面打通：直接检查用户自己在本平台发布的页面，跳过抓取 | v2 |

v2 之所以不放 v1：指纹算法（怎么算「结构雷同」才既不误报又有区分度）需要真实页面样本校准，而 v1 的抓取数据正好提供样本。先做 v1 也能验证「到底有没有人用」这个前提。

## 十、项目特有约束

- **新增公开页必须同步 `LOCALIZED_ROUTES` + `app/zh` 镜像树**，否则中文侧直接 404。本仓库前几个 PR 反复踩过这个坑，`lib/i18n/routes.test.ts` 有对等性断言兜底
- UI 文案与报告文案全部双语，进 `lib/i18n/dictionaries`
- 报告页面向公众且可索引？**建议 `noindex`**——报告内容是他人页面的检查结果，大量此类页进索引既无价值也可能引起纠纷。工具页本身要可索引
- Tailwind only，无自定义 CSS 与内联样式
- 本地 `next build` 常因 Google Fonts 拉取失败，构建以 CI 的 verify 为准

## 十一、Sandbox 成本实测（2026-08-02，已完成）

在真实 Vercel Sandbox 上跑通全流程后的实测数据。**账号为 Hobby 档**（已通过 API 确认）。

### 11.1 实测耗时

| 阶段 | 耗时 | 说明 |
|---|---|---|
| **冷启动合计** | **~29.5s** | 无快照时每次都要付：create 4.6s + dnf 装 Chromium 依赖 19.7s + 装 agent-browser 2.4s + 下载 Chromium 2.8s |
| 创建快照 | 4.7s | 一次性 |
| **快照热启动** | **0.6–0.7s** | 与官方「亚秒」一致 |
| 打开页面 | 3.7–4.2s | 真实站点 |
| 取网络请求列表 | 0.4s | |
| 关闭浏览器 | 0.5s | |
| **出结果合计** | **5.3s** | ← 用户感知延迟 |
| `sandbox.stop()` | 6.5s | **可 fire-and-forget**，不阻塞返回 |

**结论：快照是必需品，不是优化项**——差距是 29.5s 对 0.6s。

### 11.2 单次检查的资源占用

- 1 次 `Sandbox.create()`
- 内存**按 1 分钟最小增量计费**（官方明确），故 13s 的沙箱按 1 分钟计
- 默认 2 vCPU = 4 GB → `4 GB × 1/60 h = 0.0667 GB-h` / 次
- 降到 **1 vCPU = 2 GB** → `0.0333 GB-h` / 次
- Active CPU：**未直接测量**。页面加载以 I/O 等待为主（官方明确 I/O 等待不计费），粗估 2–3s/次，此数字为估算而非实测

### 11.3 Hobby 额度换算

| 维度 | Hobby 月额度 | 可支撑检查次数 |
|---|---|---|
| Sandbox Creations | 5,000 | **5,000** ← 约束项 |
| Provisioned Memory | 420 GB-h | 6,300（2 vCPU）/ 12,600（1 vCPU） |
| Active CPU | 5 h | ~6,000–9,000（按估算） |
| Snapshot Storage | 15 GB 终身 | 一个 Chromium 快照足够 |

**结论：Hobby 档每月约 5,000 次检查完全免费**，超出后创建被暂停（不产生费用）。

Pro 档参考：约 **$0.0015–0.002 / 次**，即 1,000 次约 $1.5–2，且有 $20/月额度。成本不是这个功能的障碍。

### 11.4 ⚠️ 真正的约束是吞吐，不是钱

Hobby 的 **vCPU 分配限速为 40 vCPU / 10 分钟**：

- 默认 2 vCPU → **每分钟仅 2 次检查**
- 改用 1 vCPU → 每分钟 4 次

一旦报告在投手群里被转发，十分钟内上百人点进来，绝大多数会失败。**这是比成本严重得多的风险**，且必须在架构上解决而不是靠限频掩盖：

1. **用 1 vCPU**（页面加载不吃 CPU），吞吐翻倍、内存成本减半
2. **静态预筛**（第五节已有）——无像素的页面根本不起浏览器，砍掉大部分调用
3. **异步 + 排队**：提交后立即返回「生成中」，浏览器检查排队执行，完成后报告页可见。A 档结果先出，B 档补上
4. `stop()` fire-and-forget，用户 5.3s 即可看到 A 档结果

### 11.5 实测发现的两个新约束

- **Sandbox 目前仅 `iad1` 区域**。→ 无法实现「从目标市场加载以检测地域封锁」这类检查，该想法从 roadmap 移除
- **快照在最后一次使用后 30 天过期**。→ 工具若长期无人使用，下一次检查会退回 29.5s 冷启动。缓解：挂进现有 `app/api/cron/daily` 每日触碰一次快照保活（cron 基建现成）

### 11.6 核心检查项的可行性（已验证）

`agent-browser` 提供 `network requests` 与 `network har` 子命令，实测输出包含每条请求的方法、URL、类型与状态。

**更好的消息是这个检查不需要时间戳**：只要在「打开页面之后、与同意组件交互之前」dump 一次请求列表，其中若出现已知追踪域名（`connect.facebook.net`、`googletagmanager.com`、`analytics.tiktok.com` 等），即可判定「同意前已触发」。判定逻辑是集合包含关系，不是时序比较——实现与解释都更简单，误报也更少。

## 十二、待决问题（评审时已拍板）

以下四项在 2026-08-02 评审中确认，按原推荐执行：

1. **遵守被检查站点的 robots.txt** ✅
   命中 `Disallow` 时不抓取，并如实报告「该页 robots 不允许抓取，这本身就是一条发现」——立场自洽，且把限制转化为发现项。

2. **报告链接：不可猜测 token + `noindex` + 页面明示** ✅
   报告页注明「任何持有此链接的人都能查看」。

3. **浏览器方案：Vercel Sandbox** ✅
   成本实测已完成（第十一节），结论是成本可接受、吞吐需架构解决。静态降级方案不再需要作为主路径，但保留为 Sandbox 不可用时的兜底，届时报告须标注「疑似」而非「实测」。

4. **免费额度** ✅
   限频取 **同 IP 每小时 5 次、每日 20 次**（第七节）。此值远低于 5,000/月的账号额度，真正的护栏是第 11.4 节的排队机制。

## 十三、待决问题（新增，实现前需确认）

1. **异步 UX 的具体形态**——A 档 5s 内出、B 档排队补上，是同页轮询还是先给报告链接再刷新？影响前端结构。
2. **1 vCPU 是否够用**——实测用的是默认 2 vCPU。降到 1 vCPU 前应实测一次页面加载是否明显变慢。
3. **快照保活的成本**——每日 cron 触碰一次快照会多消耗 1 次 creation + 1 分钟内存，可忽略；但需确认 cron 失败时的退化路径（退回冷启动而非报错）。

## 十四、验证策略

- **单元**：SSRF 校验器是重点——私网各段、IPv4-mapped IPv6、重定向逐跳、超限中止，逐条断言。这是本功能测试价值最高的部分
- **集成**：用本地起的靶站覆盖「隐私链接 404」「多跳重定向」「robots 屏蔽」「像素同意前触发」等场景，避免依赖外网
- **E2E**：贴 URL → 出报告 → 分享链接可访问；中文侧同样
- **安全**：针对 SSRF 单独写一组「必须被拒绝」的用例（`http://169.254.169.254/`、`https://[::ffff:127.0.0.1]/`、跳转到内网的多跳链）

## 十五、风险

| 风险 | 缓解 |
|---|---|
| SSRF 被利用探测内网 | 第六节全部条目为必需项，且有专门测试组 |
| 成本失控（浏览器调用） | 静态预筛 + 限频 + 缓存；上线后按 `browser_ran` 核算 |
| 报告被当成「过审保证」 | 文案红线（第二节）+ 报告页显式声明 |
| 抓取第三方页面引发投诉 | 遵守 robots（待决 1）+ 明确的 UA 标识 + 报告页提供联系方式 |
| 误报损伤可信度 | A 档全部为客观事实；C 档不给结论；B 档降级时必须标注「疑似」 |
