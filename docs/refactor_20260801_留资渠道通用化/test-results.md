## 等价性判据的实测有效性

判据不是空对空的假绿：52 套模板共 **165 个 CTA 条目**，无一模板清单为空。

判据在实施过程中**真的拦下过错误**：把被置空的 CTA 转成 `{kind:"primary"}` 时，主渠道为表单的 13 套模板会把空按钮变成能点的 `#lead-form`，9 个用例当场报红。

## 实施中发现并修复的缺陷

以下六个缺陷都不在原设计与计划里，均由实测发现。按发现顺序：

### 1. 落点漏网口径高估一个量级（文档错误）

设计文档称「约 86 处保留模板占位号」，那是数源码里的 `link: WHATSAPP` 常量引用。实例化后的 draft 实测 165 个落点：置空 87 / 其他 URL 37 / 锚点 28 / **占位号 13**。缺陷成立但规模小得多。

### 2. 空链接兜底规则会破坏等价性

原规则「空链接 → 看 `leadForm.enabled`」。但 `blankPrimaryCtaLinks` 跳过锚点，空链接必然原本是深链；而 PR #144 后 52 套模板全部启用表单，按原规则会兜成 `primary: "form"`，把原本解析为空的 CTA 变成 `#lead-form`。改为兜底到「值为空的渠道」。

### 3. WhatsApp 预填消息会被整批丢掉

模板里 **46 个 wa.me 链接全部带 `?text=`，没有一个是纯号码**。原设计只把号码收进 `contact`，预填全丢——而预填是这条深链最有价值的部分（首屏问评估、悬浮问咨询、套餐区问具体项目）。

已给 `CtaTarget` 加 `prefill` 字段。**等价性判据没抓到这个**：原正则行尾锚定，带 `?text=` 的链接根本没匹配上、全被当 `url` 保留——测试是诚实的（链接确实没变），但它掩盖了「对最重要的渠道这次转换等于没做」。

### 4. 被置空的 CTA 转成了永久死链

`{kind:"url", url:""}` 用户以后填了号码也活不过来。改为渠道引用。等价性判据两边都是 `null`，同样抓不到。

### 5. 编码往返不是逐字节的

`%27` 解码成 `'` 后，`encodeURIComponent` 不会编回 `%27`。**迁移在本地首次执行时当场中止并回滚**——这正是自校验设计的预期行为。已改用严格编码（补 `!'()*`），并加往返兜底：转换后解析回来若与原链接不一致就原样保留为 url，避免一条手写链接把整次部署卡死。

### 6. 备份表形同虚设（最危险的一个）

`pgm.sql()` 是**排队**执行的，会排在 `pgm.db.query()` 的 UPDATE 之后，备份到的是已转换的数据，**回滚彻底失效**。发现方式是执行 `migrate:down` 后核对数据而不是假定它有效。

已改用 `pgm.db.query` 建备份，并用专门的探针迁移验证时序（备份=`BEFORE` / 现值=`AFTER`）。

### 7. 迁移不幂等

在已转换的数据上重跑会读到 `undefined` 的 link 而崩。崩溃本身安全（事务回滚），但已加 `isConverted` 守卫直接放行。

### 8. 字段校验静默失效（红线相关）

`validate.ts` 按**键名**遍历 draft 做字段校验。CTA 的 `link` 改名成 `target.url` 后，`validateLink` 什么都不再校验——**连「交易语义链接拦截」这条项目硬红线也一起失效**。已把映射键改为 `url`，并把 `contact` 纳入遍历范围。

### 9. 表单锚点 href 渲染成 React 报错文本（只有真机能发现）

`LEAD_FORM_ANCHOR_ID` 定义在 `LeadForm.tsx`，那是 `"use client"` 模块。服务端的 `channel-href.ts` import 它拿到的是**客户端引用代理**而不是字符串值，拼进 `href` 变成一段 React 报错文本——13 套以表单为主转化的模板首屏按钮全是死的。

**1067 个单元测试全部通过，因为它们跑在 Node 里没有 RSC 边界。** 只有浏览器走查能发现。已把常量抽到独立的 `leadFormAnchor.ts`。

## 结论

阶段 1 的完成定义是「什么都没变」。达成，但代价是过程中修掉 9 个缺陷——其中 3 个（#6 备份失效、#8 红线失效、#9 锚点死链）如果漏到生产，损害都不可小觑。

值得记下的方法论：**等价性判据很强，但它只覆盖它能表达的东西**。#3 #4 都是判据两侧结果相同、实质却错了；#9 更是任何单元测试都测不到。判据 + 真机走查缺一不可。

## 阶段 2 发现并修复的缺陷

### 模板占位号会随备用渠道漏出去

`blankPrimaryCtaLinks` 只清主渠道值（阶段 1 为保持等价而收窄）。但 `b2b-sourcing` 主渠道是表单、悬浮按钮却钉在 whatsapp 上——只清主渠道的话，用户新建这套模板，悬浮按钮就指着模板占位号 `+15551234567`，全靠发布时的全文扫描兜底。

已改为 `blankTemplateContacts`：清空全部渠道值。模板里的号码和邮箱都是虚构的，留着任何一个都可能被原样发布出去。`PLACEHOLDER_CONTACTS` 全文扫描随之删除——号码只存在 `contact` 一处且实例化即清空，占位号无处可藏。

## 遗留

- `prefill`（WhatsApp 预填语）在主渠道切成表单后仍留在 target 上。目前无害（表单不读它），且用户切回 WhatsApp 时那句话仍然正确，故**刻意保留**。
- 阶段 3：52 套模板补齐 `textByChannel`、`GenerateBriefDialog` 的 `CTA_CHANNELS` 收口写入 `contact`、画廊筛选语义调整。
