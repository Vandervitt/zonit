# 落地页租户路由移出 proxy · 定位、方案与效果

日期：2026-10-28
相关 PR：#230
前置：#227（函数与库迁至新加坡 sin1 / aws-ap-southeast-1），见 `docs/perf_20261027_后台访问性能优化/test-results.md`

## 1. 问题

迁到新加坡后，需要评估欧美访客打开客户落地页的代价，以及能否靠 CDN 缓存抵消。

## 2. 定位（Globalping 公共探针，生产）

同一组探针连测 3 轮，下表取第 2–3 轮首字节（ms）：

| 请求 | 法兰克福 | 伦敦 | 阿什本 | 圣保罗 | 新加坡 |
|---|---|---|---|---|---|
| 静态资源（不经 proxy） | 15–30 | 10–30 | 16–20 | 10–16 | 16–20 |
| 首页 / 定价（经 proxy，CDN 命中） | 35–55 | 31–40 | 31–58 | 27–46 | 31–47 |
| 租户域名不查库路径（proxy 直接 404） | 25–36 | 25–63 | 35–67 | — | 30–33 |
| **租户域名根路径（proxy 查库）** | **1150** | **1200** | **1600** | **2900** | **55** |

结论：

- proxy 在**访客就近区域**执行（fra1 / lhr1 / iad1），对 CDN 缓存页只加 20–40ms，营销站不受迁移影响。
- 落地页的大头是 proxy 里的 `resolveTenantRoute`：从欧美直连新加坡库，约 7 个往返（疑似每次新建连接），1.1–1.6 秒，圣保罗 2.9 秒。
- 这段发生在任何缓存之前，**只给页面加 CDN 缓存无效**。

## 3. 方案

| 改动 | 说明 |
|---|---|
| `lib/proxy/tenant-proxy.ts` | 只校验路径形状，改写到 `/p` 并透传 `x-tenant-host`、规范化后的 `x-tenant-path`，不再查库 |
| `app/p/page.tsx` | 租户页唯一入口，在 sin1 带缓存解析「域名 + 路径 → 落地页 / 政策子页」，未绑定 `notFound()` |
| `lib/landing-pages/tenant-target.ts` | 原 proxy 的解析规则（精确绑定优先，政策子页回退） |
| `resolveTenantRouteCached` / `invalidateTenantRoutes` | tag `tenant-routes` + `published-pages`，立即过期；300s 兜底 |
| 写入点失效 | 发布、域名启停 / 验证 / 删除、删页面；配额下线与禁用账号经全量 tag 覆盖 |

取舍：经接口的操作仍即时生效（E2E 覆盖）；**直接改库**（运维手工 SQL）最长 5 分钟后生效，此前 proxy 每次实时查库是即时的。

## 4. 效果（Preview + Globalping，同一组探针 4 轮，取第 2–4 轮中位数，ms）

| 探针 | 改前：生产 proxy 查库（仅 404，不渲染） | 改后：Preview 完整落地页 200 | 降幅 |
|---|---|---|---|
| 法兰克福 | 1208 | 409 | −66% |
| 伦敦 | 1294 | 447 | −65% |
| 阿什本 | 1638 | 528 | −68% |
| 洛杉矶 | 1267 | 427 | −66% |
| 圣保罗 | 2842 | 829 | −71% |
| 新加坡 | 78 | 99 | 持平 |

口径说明：

- 「改前」是生产上一个**未绑定**的子域名：proxy 查库后直接 404，**还没算渲染与回新加坡那一跳**，真实的旧落地页只会更慢。所以上表低估了降幅。
- 「改后」是完整落地页（含渲染），`x-vercel-id` 为 `fra1::sin1` 等：跨区只剩边缘 → 函数一跳。
- 同一 Preview 上 proxy 直接 404 的路径在欧美是 190–350ms，而生产同类路径是 25–60ms：Preview 的 proxy 自身就多一段开销。上线生产后的落地页预计比表中「改后」再低约 150ms，需合并后复测确认。

其他路径（改后，第 2–4 轮）：

| 探针 | 政策页 `/privacy` | 未绑定 `/nope`（页面 404） |
|---|---|---|
| 法兰克福 | 399–419 | 385–394 |
| 阿什本 | 514–559 | 516–534 |
| 圣保罗 | 779–854 | 733–796 |

### 4.1 合并后生产复测（同一请求前后对比）

同一个未绑定子域 `zz-latency-probe.zapbridge.site/`：改前是 proxy 查库后 404，改后是页面函数带缓存解析后 404。同组探针 4 轮，取第 2–4 轮中位数（ms）：

| 探针 | 改前 | 改后 | 降幅 |
|---|---|---|---|
| 法兰克福 | 1208 | 387 | −68% |
| 伦敦 | 1294 | 279 | −78% |
| 阿什本 | 1638 | 330 | −80% |
| 洛杉矶 | 1267 | 261 | −79% |
| 圣保罗 | 2842 | 398 | −86% |

同轮对照：生产 proxy 直接 404 的路径仍是 25–65ms，营销首页 CDN 命中 32–120ms，均不受影响。生产比 Preview 再低约 100–400ms，与「Preview 的 proxy 多一段开销」的判断一致。

## 5. 验证

- 单测 1915 全过；新 proxy 测试在旧实现上失败（mock 查库即抛错）。
- 租户相关 E2E 19/19：landing-pages-flow / seo / footer-compliance / leads / capi。
- E2E 新增「停用域名 → 404 → 启用 → 200 → 下线 → 404」；去掉 PATCH 的失效调用后该用例失败，确认守得住。
- `next build`、lint、tsc 通过。

## 6. 过程中的坑

| 坑 | 表现 | 处理 |
|---|---|---|
| Preview 不走租户路由 | `NEXT_PUBLIC_APP_URL` 只配了 Production，`lib/host.ts` 在未配置时把所有域名当平台域，租户域名直接落到营销首页 | 为本分支加 Preview 级变量后重建 |
| Preview 部署保护 | 匿名请求 302 到 Vercel SSO，Globalping 进不去 | 只给测试域名加 Deployment Protection Exception，不关全局保护 |
| E2E fixture 撞缓存 | 直接写库的 fixture 不失效缓存，复用固定 slug / 域名时上一轮末尾的「已下线」被缓存住，下一轮一上来 404 | fixture 每轮独立 slug 与域名 |
